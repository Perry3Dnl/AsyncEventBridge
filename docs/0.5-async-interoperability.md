# 0.5 async interoperability

AsyncEventBridge 0.5 expands the package from individual event conversions into a small interoperability layer for event-driven async workflows.

The boundary stays deliberately narrower than Rx or a general-purpose async LINQ library. The package owns coordination where event subscription lifetime, cancellation, deterministic cleanup, and async/event conversion semantics matter.

## Existing pillars carried forward from 0.4

- one-shot event waits through generated `<EventName>Async(...)` APIs and `EventAwaiter`;
- repeated event consumption through generated `<EventName>Stream(...)` APIs and `EventStream`;
- third-party and legacy event adaptation through `GenerateAsyncEventsFor`;
- sender-aware occurrences;
- lifecycle-safe multi-wait coordination through `EventComposition`;
- async-to-event bridges for `Task`, `ValueTask`, and `IAsyncEnumerable<T>`.

## First 0.5 workflow primitive: stream-until-event

`EventStreamComposition.TakeUntil` links an async stream to another cancellable async wait:

```csharp
await foreach (var value in sensor.ValueChangedStream()
    .TakeUntil(
        token => sensor.DisconnectedAsync(token),
        cancellationToken))
{
    Process(value);
}
```

The stop wait is created per enumeration. It and the source enumerator receive the same coordination token.

If the stop wait completes first, the source is cancelled, observed, and disposed before the composed stream completes. If the source completes or faults first, the stop wait is cancelled and observed before completion is reported.

If the source produces a value and the stop wait are both complete when a move boundary is observed, the stop wait wins and that value is not published.

A faulted or cancelled stop wait is not treated as successful termination: its outcome is propagated. Cleanup failures are preserved using the same primary-outcome-first policy as the 0.4 wait and stream runtime.

Deterministic cleanup means completion can depend on custom sources and stop waits honoring cancellation or otherwise eventually completing.

## Second 0.5 workflow primitive: start-after-event

`EventStreamComposition.StartAfter` defers source enumeration until a cancellable activation wait completes successfully:

```csharp
await foreach (var value in sensor.ValueChangedStream()
    .StartAfter(
        token => sensor.ConnectedAsync(token),
        cancellationToken))
{
    Process(value);
}
```

The source enumerator is not created before activation. For event-backed streams this is stronger than merely filtering values: the underlying source event is not subscribed until the start wait succeeds.

A faulted or cancelled start wait propagates its outcome and the source never starts. External cancellation cleans the pending activation wait using the same deterministic cleanup contract as one-shot event waits.

## Complete lifecycle composition

`StartAfter` and `TakeUntil` compose into an inactive/active/stopped workflow without introducing a larger state-machine API:

```csharp
await foreach (var value in sensor.ValueChangedStream()
    .StartAfter(token => sensor.ConnectedAsync(token))
    .TakeUntil(token => sensor.DisconnectedAsync(token)))
{
    Process(value);
}
```

The outer `TakeUntil` begins observing termination before the inner `StartAfter` has activated the source. If termination occurs first, the pending start wait is cancelled and observed and the source is never subscribed.

This composability is intentional: 0.5 should prefer a few orthogonal lifetime primitives over monolithic workflow objects when the same semantics can be expressed safely through composition.

## Repeating lifecycles

`EventStreamComposition.RepeatBetween` promotes the one-shot active window into a repeating lifecycle:

```csharp
await foreach (var value in sensor.ValueChangedStream()
    .RepeatBetween(
        token => sensor.ConnectedAsync(token),
        token => sensor.DisconnectedAsync(token),
        cancellationToken))
{
    Process(value);
}
```

The repeating workflow has three logical states: inactive, active, and cancelled/faulted. While inactive it waits for activation. After activation it creates a fresh source enumeration and consumes it until deactivation or source completion. It then cleans that cycle and rearms activation.

A successful deactivation observed before activation does not terminate the overall stream; it closes the current inactive cycle and rearms. This keeps repeated connect/disconnect workflows stable when redundant or out-of-order stop notifications occur.

A fresh source enumeration is created for every active cycle. That is the intended behavior for cold event-stream adapters because each lifecycle window owns its own event subscription. A finite non-event source therefore restarts on every activation as well.

Lifecycle or source faults terminate the repeating stream. External cancellation owns the whole repeated lifetime. Cleanup failures remain observable using the same primary-outcome-first rules as the one-shot primitives.

The implementation deliberately composes `StartAfter` and `TakeUntil` rather than creating a second independent cleanup state machine. This keeps repeated lifecycle behavior aligned with the already-tested primitive contracts.

## Observable lifecycle transitions

`RepeatBetweenWithLifecycle` exposes the same repeated lifetime while preserving lifecycle boundaries in the returned stream:

```csharp
await foreach (var item in sensor.ValueChangedStream()
    .RepeatBetweenWithLifecycle(
        token => sensor.ConnectedAsync(token),
        token => sensor.DisconnectedAsync(token),
        cancellationToken))
{
    switch (item.Kind)
    {
        case EventStreamLifecycleEventKind.Activated:
            BeginCycle(item.Cycle);
            break;

        case EventStreamLifecycleEventKind.Value:
            Process(item.Cycle, item.Value);
            break;

        case EventStreamLifecycleEventKind.Deactivated:
        case EventStreamLifecycleEventKind.SourceCompleted:
            EndCycle(item.Cycle, item.Kind);
            break;
    }
}
```

`EventStreamLifecycleEvent<T>` carries `Kind`, one-based `Cycle`, `HasValue`, and `Value`. `Value` is valid only for the `Value` kind and throws otherwise.

The stable lifecycle kinds are:

```text
Activated       = 0
Value           = 1
Deactivated     = 2
SourceCompleted = 3
```

A cycle number is allocated only after activation succeeds. Stop-before-start therefore rearms silently and does not manufacture a transition or consume a cycle number.

`Deactivated` means the configured stop wait completed successfully. `SourceCompleted` means the source enumeration ended naturally. Source faults, lifecycle-wait faults, cleanup failures, and external cancellation remain terminal exceptions rather than being converted into marker values.

The observable form still composes the same `StartAfter` / `TakeUntil` contracts internally, so boundary ordering and deterministic cleanup do not fork into a separate semantic model.

## Race-safe state conditions

Event-driven APIs often expose both a current state property and a change event. Waiting only for the next event is incorrect when the desired state is already active. Checking state and then subscribing is also incorrect because a transition can happen between those two operations.

`EventCondition.WaitUntilAsync` uses subscribe-before-check ordering on every attempt:

```csharp
ConnectionState state = await EventCondition.WaitUntilAsync(
    () => client.State,
    state => state == ConnectionState.Connected,
    token => client.StateChangedAsync(token),
    cancellationToken);
```

The change wait is armed first. The current state is then read and tested. If the state already satisfies the predicate, the temporary change wait is cancelled and observed before returning. If the state does not match, the method waits for a change notification and then repeats the subscribe-before-check sequence.

This ordering closes both common races:

```text
check -> transition -> subscribe -> wait forever
subscribe -> transition -> check -> transition is still observed
```

Spurious notifications are safe: they cause another attempt. State-read or predicate failures remain primary outcomes while the already-armed change wait is cancelled and observed using the same deterministic cleanup philosophy as the rest of the package.

The primitive is intentionally state/event specific rather than a polling API. It composes naturally with `StartAfter`, `RepeatBetween`, and `RepeatBetweenWithLifecycle` when activation depends on both current state and future state transitions.

## Scope guardrails

0.5 may add a small number of workflow primitives when they solve event-specific lifetime or coordination problems. It should not grow a parallel implementation of general async LINQ operators, schedulers, observable contracts, or arbitrary stream transformations.
