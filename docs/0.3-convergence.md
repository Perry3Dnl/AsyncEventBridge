# AsyncEventBridge 0.3.0 convergence plan

Version 0.3.0 is a convergence release. Its purpose is to move every supported AsyncEventBridge edition onto one branch, one version line, and one release-readiness process.

Feature parity is not a release requirement. Platform-specific features may remain specific to modern .NET or Unity when the underlying runtime capability does not exist elsewhere. Release-readiness parity is required.

## Product tracks

| Track | Location on main | 0.3 release role |
| --- | --- | --- |
| Modern .NET | repository root / `src/AsyncEventBridge` | native `net10.0` runtime and modern feature surface |
| .NET Standard compatibility | `compat/netstandard2.0` | stable `netstandard2.0` compatibility asset and regression baseline |
| Unity | `Packages/com.perry3d.async-event-bridge` plus Unity generator/tests | UPM distribution and Unity-specific integration |
| Roslyn generators | `src/AsyncEventBridge.Generators` and `src/AsyncEventBridge.Unity.Generators` | generated facades for NuGet and Unity consumers |

## Version rule

The repository version in `Directory.Build.props` is the release source of truth.

For 0.3.0:

- root version: `0.3.0`;
- modern NuGet validation package: `0.3.0`;
- compatibility NuGet validation package: `0.3.0`;
- Unity `package.json`: `0.3.0`;
- release/tag version: `0.3.0`.

CI must fail when the Unity manifest does not match the shared version. Compatibility projects intentionally inherit the root version instead of carrying a second version file.

## Definition of equal completion

A track is 100% release-ready only when every applicable gate below is green. A track is not considered complete merely because its code compiles.

### Common gates

- [ ] source builds from a clean checkout;
- [ ] automated tests pass;
- [ ] public/package-facing API is intentionally documented;
- [ ] package metadata and version are correct;
- [ ] an isolated consumer validates the produced artifact;
- [ ] lifecycle/cancellation/disposal behavior has regression coverage where applicable;
- [ ] CI validates the track on the supported host matrix;
- [ ] release documentation describes the actual shipped surface.

### Modern .NET gates

- [x] `net10.0` implementation and tests exist on the convergence line;
- [x] package and symbol-package validation exists;
- [x] packaged runtime consumer exists;
- [x] Native AOT/trimming smoke validation exists;
- [x] Windows/macOS build and test validation exists;
- [x] final 0.3 package contains both modern and compatibility runtime assets in one NuGet validation artifact.

### .NET Standard 2.0 gates

- [x] complete compatibility source/test baseline is present on the convergence line;
- [x] compatibility solution builds and tests independently in unified CI;
- [x] compatibility package smoke and runtime consumers are part of unified CI;
- [x] compatibility version is inherited from the root 0.3 version;
- [x] compatibility runtime is consolidated with the modern runtime in the unified 0.3 NuGet validation artifact;
- [ ] compatibility docs/public API contract must be reviewed against the final 0.3 packaging shape.

### Unity gates

- [x] UPM package source, tests, sample, generator source, and compile smoke are present on the convergence line;
- [x] UPM manifest version is validated against the shared 0.3 version;
- [x] Unity portable core is checked byte-for-byte against the compatibility baseline;
- [x] Unity runtime is compiled against Unity API stubs in unified CI;
- [ ] bundled Roslyn analyzer binary must be rebuilt from the 0.3 source and verified byte-for-byte against the build;
- [ ] Unity Editor/Test Runner acceptance must pass on the actual package;
- [ ] IL2CPP acceptance must pass on the actual package;
- [ ] final Unity documentation and Asset Store/release metadata must be reviewed for 0.3.

## Convergence phases

### Phase A — put every track on one line

- [x] create `release/0.3.0-convergence` from modern `main`;
- [x] import the Unity UPM package, Unity generator, tests, and sample;
- [x] import the complete .NET Standard 2.0 baseline under `compat/netstandard2.0`;
- [x] set the shared version to `0.3.0`;
- [x] set Unity `package.json` to `0.3.0`;
- [x] move documentation from independent branch language to one release line;
- [x] add unified CI lanes for modern, compatibility, and Unity.

### Phase B — make NuGet a single 0.3 artifact

The final NuGet release should have one package ID/version and expose the correct runtime asset to each consumer.

Target shape:

```text
AsyncEventBridge 0.3.0
├── lib/net10.0/AsyncEventBridge.dll
├── lib/netstandard2.0/AsyncEventBridge.dll
├── tools/generators/modern/AsyncEventBridge.Generators.dll
├── tools/generators/compat/AsyncEventBridge.Generators.dll
├── buildTransitive/AsyncEventBridge.targets
├── README.md
└── assets/AsyncEventBridge.png
```

Remaining work:

- [x] combine independently validated modern and compatibility assets through `packaging/AsyncEventBridge.Package`;
- [x] select the validated modern or compatibility generator per consumer target framework through `buildTransitive/AsyncEventBridge.targets`;
- [x] validate dependency groups so `Microsoft.Bcl.AsyncInterfaces` is required only by the compatibility target;
- [x] run modern and compatibility package-smoke/runtime consumers against the same unified package, plus the modern Native AOT consumer;
- [ ] produce matching symbol/source metadata for both runtime assets.

### Phase C — bring Unity to the same release confidence

- [ ] regenerate and commit the Unity analyzer binary from the 0.3 source;
- [ ] restore byte-for-byte analyzer reproducibility in CI;
- [ ] run Unity Runtime and Editor tests in an actual supported Unity version;
- [ ] run an IL2CPP package acceptance build;
- [ ] validate the importable sample from the packaged UPM artifact.

### Phase D — release closure

- [ ] review public API/documentation differences between tracks and mark platform-specific APIs clearly;
- [ ] make the unified workflow green on Linux, Windows, and macOS;
- [ ] merge convergence work into `main`;
- [ ] treat `dotnet-latest`, `base/netstandard2.0`, and `unity` as historical/reference branches rather than release lines;
- [ ] create the 0.3.0 release/tag only after all applicable gates are complete.

## Feature policy for 0.3

New features are optional during convergence. A track does not need a new feature merely to justify the 0.3 version.

Work should be prioritized in this order:

1. correctness regressions;
2. packaging/version convergence;
3. release and host validation;
4. documentation/API consistency;
5. low-risk quality improvements;
6. new functionality only when it does not delay convergence.

This keeps 0.3 focused on making the product family equally releasable instead of expanding one edition while another falls behind.
