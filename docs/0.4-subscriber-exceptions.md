# 0.4 subscriber exception policy

AsyncEventBridge publishes asynchronous outcomes through ordinary .NET events. A bridge event subscriber can therefore throw while the bridge is publishing a value or terminal outcome.

0.4 makes the handling of those exceptions explicit and configurable.

## Default behavior

The default remains compatible with earlier releases:

```csharp
var options = new EventBridgeOptions
{
    SubscriberExceptionPolicy =
        EventBridgeSubscriberExceptionPolicy.TraceAndContinue,
};
```

If a subscriber throws:

1. the exception is written through `System.Diagnostics.Trace.TraceError`;
2. that subscriber's exception is isolated;
3. remaining subscribers are still invoked;
4. bridge processing continues.

This applies to `Completed`, `Faulted`, `Cancelled`, and `EventStreamBridge<T>.Value`.

## Policies

### TraceAndContinue

```csharp
SubscriberExceptionPolicy =
    EventBridgeSubscriberExceptionPolicy.TraceAndContinue
```

This is the default. Subscriber failures are traced and dispatch continues.

### ReportAndContinue

```csharp
var options = new EventBridgeOptions
{
    SubscriberExceptionPolicy =
        EventBridgeSubscriberExceptionPolicy.ReportAndContinue,

    SubscriberExceptionObserver = exception =>
        logger.LogError(exception, "Bridge subscriber failed"),
};
```

The configured observer receives every subscriber exception synchronously on the bridge publication path.

`SubscriberExceptionObserver` is required when this policy is selected. Invalid configuration is rejected when the bridge is created.

If the observer itself throws, AsyncEventBridge isolates that observer failure, writes it through `Trace.TraceError`, and continues dispatching. A reporting hook therefore cannot destabilize the bridge.

### IgnoreAndContinue

```csharp
SubscriberExceptionPolicy =
    EventBridgeSubscriberExceptionPolicy.IgnoreAndContinue
```

Subscriber failures are ignored and remaining subscribers continue.

This mode is intended for applications that deliberately provide their own isolation boundary or do not want bridge-level diagnostics. It should not be used merely to hide unexpected failures.

## Why there is no Propagate policy

Bridge publication is normally driven by asynchronous observation:

```text
Task / ValueTask / IAsyncEnumerable<T>
              |
              v
        bridge observer
              |
              v
          .NET event
```

There is usually no synchronous application caller waiting on the event invocation. Throwing a subscriber exception out of the dispatcher would therefore tend to fault an internal fire-and-forget observation task rather than return the exception to useful application code.

That creates worse failure semantics:

- the application may receive an unobserved-task failure;
- later subscribers may not execute;
- stream enumeration can stop for a subscriber-side problem;
- task bridges and stream bridges would have different practical propagation behavior.

0.4 therefore keeps subscriber isolation as the invariant for all policies. Applications that need subscriber failures as data should use `ReportAndContinue`.

## Options are snapshotted

`EventBridgeOptions` is read when `ToEventBridge(..., options)` creates the bridge.

Changing the options instance afterwards does not change an already-created bridge. This avoids races when an options object is shared or reused.

## API

Modern .NET supports options overloads for:

```csharp
Task.ToEventBridge(options)
Task<T>.ToEventBridge(options)
ValueTask.ToEventBridge(options)
ValueTask<T>.ToEventBridge(options)
IAsyncEnumerable<T>.ToEventBridge(options)
```

The .NET Standard 2.0 and Unity portable core expose the corresponding options overloads for the async source types available on that baseline:

```csharp
Task.ToEventBridge(options)
Task<T>.ToEventBridge(options)
IAsyncEnumerable<T>.ToEventBridge(options)
```

Calling `ToEventBridge()` without options continues to use `TraceAndContinue`.

## Threading

The observer callback executes synchronously on the same publication path that invoked the throwing subscriber. It must therefore be fast, thread-safe, and non-blocking from the application's perspective.

Different bridge instances can publish concurrently, so an observer shared between bridges can also be called concurrently.
