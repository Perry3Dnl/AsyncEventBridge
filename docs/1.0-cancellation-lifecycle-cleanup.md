# 1.0 cancellation, lifecycle, and cleanup contract

This document defines the stable AsyncEventBridge 1.0 termination and ownership semantics.

The package deliberately treats cancellation, timeout, source failure, and cleanup as separate concerns. Cleanup must not silently replace the operation outcome that caused cleanup to begin.

## Primary-outcome-first rule

When an operation has a primary outcome and cleanup also fails, the primary outcome is preserved first.

| Primary outcome | Cleanup | Observable result |
| --- | --- | --- |
| Success | Success | Original success |
| Success | Failure | Cleanup exception |
| Fault | Success | Original fault |
| Fault | Failure | `AggregateException`: primary fault first |
| Cancellation | Success | Cancellation |
| Cancellation | Failure | `AggregateException`: `OperationCanceledException` first |
| Timeout | Success | `TimeoutException` |
| Timeout | Failure | `AggregateException`: timeout first |

When cleanup fails, the final operation is faulted even if the primary outcome was cancellation.

## Pre-cancellation

A pre-cancelled caller token must fail before an event subscription or state-change wait is armed where the API owns that setup boundary.

In particular:

- `EventAwaiter.WaitAsync` does not subscribe for a pre-cancelled token;
- `EventCondition.WaitUntilAsync` does not create its temporary change wait for a pre-cancelled token;
- lifecycle composition propagates caller cancellation and cleans any participants already started by that composition operation.

## Event waits

`EventAwaiter.WaitAsync` owns:

- event subscription;
- event unsubscription;
- cancellation registration;
- timeout timer registration.

Exactly one primary terminal outcome wins:

- matching event;
- predicate failure;
- caller cancellation;
- timeout;
- subscription/setup failure.

Cleanup then runs once.

A timeout is represented by `TimeoutException`. It is not converted into cancellation.

`Timeout.InfiniteTimeSpan` disables the timeout.

Modern .NET overloads can use `TimeProvider` so timeout behavior can be controlled deterministically.

## Event streams

An event stream subscribes when enumeration starts and unsubscribes when enumeration terminates.

Termination can come from:

- caller/enumerator cancellation;
- predicate failure;
- explicit enumerator disposal;
- source-side/channel failure.

Early `DisposeAsync()` performs unsubscription and surfaces unsubscribe failures.

If a stream primary failure and unsubscription both fail, the primary failure remains first in the aggregate.

## EventCondition

`EventCondition.WaitUntilAsync` arms the state-change wait before reading current state.

That ordering closes the check-then-subscribe race.

If the state is already satisfied:

1. the temporary wait is cancelled;
2. that wait is observed;
3. cleanup completes;
4. the method returns.

Spurious state-change notifications are permitted. The method rearms and reads a fresh state snapshot.

A caller cancellation that wins while a state-change wait is active cancels and observes that wait before returning cancellation.

Wait factories are expected to honor the cancellation token supplied by `EventCondition`. A wait implementation that ignores cancellation can delay deterministic cleanup.

## EventComposition

`WaitAnyAsync` cancels and observes losing waits before returning.

`WaitAllAsync` cancels and observes still-pending siblings after a fault or cancellation.

Composition therefore owns the cancellation lifetime used for its child wait factories.

Expected loser cancellation is treated as cleanup, not as an additional failure. A real cleanup failure from a losing wait remains observable.

Startup is transactional: if a later wait factory fails to start, previously started waits are cancelled and observed before the startup failure is rethrown.

## Event-stream lifecycle composition

`StartAfter`, `TakeUntil`, `RepeatBetween`, and `RepeatWhile` own the coordination tokens they create.

The active source and lifecycle wait are cleaned before the composed operation reports completion.

For `TakeUntil`, if a source value and a successful stop are both already complete at the observed boundary, the stop wins and that value is not published.

Repeated lifecycle operators create a fresh source enumeration for each active cycle.

External cancellation is terminal.

Successful lifecycle stop or natural source completion can be a per-cycle boundary where the repeating operator contract says another cycle should be armed.

## Task and ValueTask bridges

`EventBridge` and `EventBridge<T>` do not own cancellation of the supplied task/value task.

They observe the supplied operation and publish at most one terminal event:

- `Completed`;
- `Faulted`;
- `Cancelled`.

`Dispose()` suppresses a terminal publication that has not started and releases bridge-owned subscriber references.

A publication that already captured its subscriber snapshot is allowed to finish.

There is no `DisposeAsync()` because these one-shot bridges do not own asynchronous enumerator cleanup.

## Async-stream bridges

`EventStreamBridge<T>` owns source enumeration after `Connect()`.

`Dispose()`:

- marks the bridge owner-disposed;
- clears future subscriber references;
- requests cancellation;
- suppresses future value/terminal publication;
- does not wait for source cleanup or an already-running subscriber.

`DisposeAsync()` additionally waits for:

- the bridge enumeration loop;
- source enumerator disposal;
- publication already in flight on that loop.

After `DisposeAsync()` completes, the bridge will not invoke additional event handlers.

The bridge cannot forcibly terminate an `IAsyncEnumerable<T>` source that ignores cancellation or never returns from `MoveNextAsync()` / `DisposeAsync()`.

## Source OperationCanceledException classification

For `EventStreamBridge<T>`, a source-thrown `OperationCanceledException` is published as `Cancelled` only when the bridge lifetime token was actually cancelled.

An unrelated `OperationCanceledException` from the source is a fault.

This avoids treating arbitrary source failures as bridge cancellation merely because they use the same exception type.

## Owner disposal does not publish Cancelled

Owner-triggered disposal suppresses bridge publication.

It does not synthesize a `Cancelled` event.

The `Cancelled` event represents cancellation observed from the connected asynchronous operation, not disposal of the bridge object itself.

## Subscriber exceptions

Bridge subscriber exceptions are isolated from bridge lifetime semantics.

One subscriber failure does not:

- stop remaining subscribers in the captured invocation list;
- convert successful source completion into a bridge fault;
- alter disposal state.

Reporting behavior is controlled by `EventBridgeOptions`.

## Publication snapshots

Each bridge event publication uses a captured subscriber snapshot.

Handlers added or removed while that publication is already in flight affect later publications only.

Disposal during a captured publication does not truncate the remainder of that snapshot.

## 1.0 stability rule

These semantics are part of the 1.0 behavioral contract.

Future releases may add new APIs, but existing cancellation, timeout, cleanup ordering, and disposal boundaries should not change without a major-version justification.
