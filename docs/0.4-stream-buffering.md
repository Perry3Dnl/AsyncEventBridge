# 0.4 event-stream buffering contract

> **1.0 stabilization note:** this historical 0.4 contract uses the pre-1.0 name `DropNewest` for the mode that rejects an incoming write at capacity. The 1.0 API renames that mode to `DropWrite` to match `System.Threading.Channels.BoundedChannelFullMode.DropWrite`. The behavior is unchanged.

AsyncEventBridge converts synchronous event callbacks into `IAsyncEnumerable<T>`. A synchronous event producer cannot asynchronously wait for an async consumer, so the bridge must choose between buffering, dropping values, or blocking the producer.

0.4 makes that choice explicit.

## Default: lossless but unbounded

The default is:

```csharp
new EventStreamOptions
{
    FullMode = EventStreamFullMode.Unbounded,
    Capacity = 100,
};
```

`Unbounded` preserves every accepted event value. If producers continuously outpace consumers, buffered values can grow without a fixed upper bound and memory usage can grow with them.

`Unbounded` keeps numeric value `0`. In 0.4 it replaces the earlier `Grow` member before the 1.0 API freeze. The rename is intentionally source-breaking during the 0.x line because `Unbounded` describes the operational behavior directly and avoids carrying a duplicate enum alias into the long-lived API.

## Migration from earlier 0.x versions

The enum member rename is:

```text
EventStreamFullMode.Grow  ->  EventStreamFullMode.Unbounded
```

The underlying numeric value remains `0`, so numeric persistence and already-compiled enum values retain the same meaning. Source code must be recompiled with the new member name.

Name-based configuration or serialization that stores the literal string `"Grow"` must be migrated to `"Unbounded"`. AsyncEventBridge intentionally does not keep a duplicate enum alias because duplicate names for one numeric value create ambiguity for reflection and name-based serializers.

## What Capacity means

`Capacity` is a bounded-mode setting.

It is used only by:

- `DropOldest`
- `DropNewest`

It is ignored by `Unbounded`.

The default value of `100` exists so a caller can opt into a bounded mode without also having to choose a capacity immediately:

```csharp
var options = new EventStreamOptions
{
    FullMode = EventStreamFullMode.DropOldest,
    // Capacity is 100 unless changed.
};
```

It does **not** mean that the default unbounded stream has a 100-item limit, a 100-item initial allocation guarantee, or a transition point after which different behavior begins.

To make the contract mechanically testable, unbounded mode does not validate or use `Capacity`. Bounded modes require `Capacity > 0`.

## Why the default is not bounded

Changing the default to a bounded mode would make ordinary event streams silently lossy.

There is no universally correct drop policy:

- `DropOldest` favors recent state and loses history.
- `DropNewest` preserves already-buffered history and loses recent arrivals.

Either policy can corrupt application semantics when every event matters. An unbounded default therefore preserves the strongest semantic guarantee: accepted events are not silently discarded by the bridge.

The tradeoff is operational rather than semantic: applications with sustained producer/consumer imbalance must deliberately choose a bounded policy.

## Recommended bounded configuration

For state-like or telemetry-like events where recent values matter more than complete history:

```csharp
var options = new EventStreamOptions
{
    Capacity = 100,
    FullMode = EventStreamFullMode.DropOldest,
};
```

For workloads where already-buffered work should be preserved and new arrivals may be discarded:

```csharp
var options = new EventStreamOptions
{
    Capacity = 100,
    FullMode = EventStreamFullMode.DropNewest,
};
```

The modern runtime exposes `DroppedCount`, `DropObserver`, and metrics so bounded loss can be observed.

## Why there is no blocking mode

AsyncEventBridge deliberately does not block a synchronous event callback waiting for buffer space.

A producer-blocking mode can:

- change the timing semantics of the source event;
- introduce reentrancy surprises;
- deadlock when the consumer needs the producer thread or synchronization context;
- turn an observational adapter into flow control for an API that was not designed for it.

If backpressure is required, the producer should expose an asynchronous protocol rather than a synchronous .NET event.

## Cross-runtime contract

0.4 normalizes the same externally observable behavior across:

- modern .NET;
- .NET Standard 2.0 compatibility runtime;
- Unity portable core.

The underlying implementations differ: modern .NET uses `System.Threading.Channels`, while the compatibility/Unity runtime uses its portable event buffer. In all editions, `Capacity` is ignored for `Unbounded` and is a hard limit only for the two bounded drop modes.
