# 0.4 bridge lifecycle and publication contract

AsyncEventBridge event-facing bridges coordinate asynchronous sources with synchronous .NET event handlers. Version 0.4 makes the publication and disposal boundaries explicit.

## Publication uses a subscriber snapshot

When a bridge begins publishing one event, it captures the current multicast delegate under its lifecycle lock and invokes that captured subscriber list outside the lock.

This gives each individual publication snapshot semantics:

- a subscriber added while publication is already in progress does not receive that publication;
- a subscriber removed while publication is already in progress can still receive that publication if it was in the captured snapshot;
- a subscriber that disposes the bridge does not truncate the remainder of the already-captured subscriber list;
- subscriber mutation affects future publications only.

This mirrors normal multicast-delegate invocation behavior while avoiding user callbacks under the bridge lifecycle lock.

## Task and ValueTask bridges

`EventBridge` and `EventBridge<T>` publish at most one terminal event:

- `Completed`;
- `Faulted`; or
- `Cancelled`.

If owner `Dispose()` wins before terminal publication starts, no terminal event is published.

If terminal publication has already captured its subscriber snapshot, `Dispose()` does not interrupt that in-flight snapshot. The remaining captured handlers are allowed to finish.

`Dispose()` is idempotent.

Task bridges do not expose `DisposeAsync()`. Their only bridge-owned asynchronous work is observation of the supplied task/value task; there is no bridge-owned async enumerator cleanup to await.

## Stream bridges

`EventStreamBridge<T>` publishes zero or more `Value` events followed by at most one terminal outcome:

- `Completed`;
- `Faulted`; or
- `Cancelled`.

Values are published sequentially by the bridge-owned enumeration loop.

### Dispose()

`Dispose()`:

- marks the bridge owner-disposed;
- clears future subscriber references;
- requests cancellation of bridge-owned enumeration;
- suppresses future value and terminal publication;
- returns without waiting for an event handler that was already in flight.

A value or terminal subscriber snapshot captured before disposal is allowed to finish.

Owner disposal does not publish `Cancelled`.

### DisposeAsync()

`DisposeAsync()` has the same suppression semantics as `Dispose()`, but additionally waits for:

- the bridge-owned enumeration loop;
- asynchronous source-enumerator cleanup;
- any bridge event publication already in flight on that enumeration path.

After `DisposeAsync()` completes, the bridge will not invoke any further event handlers.

Multiple disposal calls are safe. If synchronous `Dispose()` happens first, a later `DisposeAsync()` can still wait for bridge-owned async cleanup that was in progress.

Do not synchronously block on `DisposeAsync()` from inside one of the bridge's own event handlers. `DisposeAsync()` waits for in-flight publication to finish, which includes the currently running handler. An asynchronous event handler may await it only if it first yields control back to the dispatcher; ordinary synchronous handlers should initiate disposal and return.

## Subscriber mutation during stream publication

For repeated `Value` publication, subscriber mutations made during value N take effect beginning with value N+1.

For example:

```text
value 1 snapshot = A, B

A is running...
caller removes B
caller adds C

value 1 still invokes A, B
value 2 observes A, C
```

Once terminal publication begins, there are no future bridge publications. Subscribers added after the terminal snapshot therefore receive no replay.

## Late subscribers and replay

Bridges do not replay values or terminal events.

Before disposal, adding a handler after terminal publication is a no-op because the terminal outcome has already been consumed by the bridge.

After owner disposal, adding a handler throws `ObjectDisposedException`.

## Terminal ordering

A stream bridge exposes at most one terminal outcome. Cancellation, natural completion, and source faults do not receive an artificial priority over one another; whichever outcome reaches the terminal-publication gate first establishes the terminal state.

A source-thrown `OperationCanceledException` is classified as bridge cancellation only when the bridge lifetime token was actually cancelled. Otherwise it is a fault.

Owner disposal suppresses terminal publication rather than converting it into a cancellation event.

## Threading

Bridge event handlers execute on the thread/context that performs bridge publication. AsyncEventBridge does not marshal portable bridge events onto a caller synchronization context.

Applications that require UI/main-thread dispatch should marshal in their subscriber or use the Unity-specific publication APIs where appropriate.

## Behavioral locks

0.4 tests explicitly lock:

- disposal before terminal publication suppresses the outcome;
- disposal after terminal publication starts lets the captured snapshot finish;
- adding a terminal subscriber during publication does not join the current snapshot;
- removing a terminal subscriber during publication does not remove it from the captured snapshot;
- disposal from a terminal subscriber does not truncate later captured subscribers;
- stream subscribers added during one value begin with the next value;
- stream subscribers removed during one value still receive the captured current value but not later values;
- synchronous stream disposal can return while an in-flight handler continues;
- async stream disposal waits for in-flight value and terminal handlers;
- disposal from a value subscriber does not truncate the current value snapshot;
- late subscribers receive no replay.
