# 1.0 stability contract

AsyncEventBridge 1.0 is a stability and adoption release.

The goal is not to maximize the number of features. The goal is to make the event/async interoperability surface complete enough, predictable enough, and well-supported enough that applications can adopt it without expecting a redesign after 1.0.

## Product boundary

AsyncEventBridge exists to bridge familiar .NET event-driven code and familiar async .NET code.

The supported programming models are:

```text
Event                 -> Task / Task<T>
Event                 -> IAsyncEnumerable<T>
Event + state/events  -> lifecycle-safe async workflow

Task / Task<T>        -> ordinary .NET events
ValueTask / ValueTask<T> -> ordinary .NET events
IAsyncEnumerable<T>   -> ordinary .NET events
```

The package owns subscription lifetime, cancellation, timeout, race avoidance, buffering, cleanup, and source-generated adapter plumbing.

### 1.0 core pillars

1. **One-shot event waits**
   - generated `<EventName>Async(...)`;
   - low-level `EventAwaiter`;
   - filtering, cancellation, timeout, deterministic time where supported.

2. **Repeated event streams**
   - generated `<EventName>Stream(...)`;
   - sender-aware occurrences;
   - explicit unbounded or bounded buffering;
   - observable drop accounting.

3. **State and lifecycle coordination**
   - `EventCondition.WaitUntilAsync`;
   - `StartAfter`, `TakeUntil`, `RepeatBetween`, and `RepeatWhile`;
   - lifecycle-marker variants where session boundaries are part of application semantics.

4. **Async-to-event bridges**
   - `Task`, `Task<T>`, `ValueTask`, `ValueTask<T>`;
   - `IAsyncEnumerable<T>`;
   - deterministic connection/disposal semantics;
   - isolated subscriber exceptions with an explicit reporting policy.

5. **Source-generated adoption path**
   - types the caller owns;
   - public third-party types the caller cannot annotate;
   - standard and compatible custom two-parameter delegates;
   - diagnostics instead of silent omission.

6. **Supported deployment lines**
   - modern .NET;
   - .NET Standard 2.0 compatibility;
   - Unity package;
   - Native AOT/trimming for the modern runtime.

## Feature-freeze rule

A new feature may enter 1.0 only when at least one of these is true:

- an ordinary event/async interop scenario cannot be expressed safely with the existing surface;
- a current API forces users into race-prone or leak-prone handwritten plumbing;
- package/runtime compatibility would otherwise break on a supported platform;
- the absence materially blocks adoption by a broad class of users.

Convenience alone is not sufficient.

The following are explicitly outside the 1.0 scope unless a concrete adoption blocker appears:

- general-purpose async LINQ;
- an Rx replacement;
- scheduler abstractions;
- dependency-injection integration;
- logging framework integrations;
- transport-specific clients;
- persistence/replay;
- application-level retry/backoff policies;
- large operator catalogs.

## API freeze requirements

Before 1.0 final:

- every exported runtime type and member is covered by API-lock tests;
- enum numeric values and option defaults are locked;
- cancellation behavior is documented for every async entry point;
- disposal/cleanup behavior is documented for every owned subscription/enumerator;
- timeout semantics are consistent across generated and low-level APIs;
- nullability annotations are reviewed as public contract;
- exception propagation and cleanup aggregation semantics are consistent;
- generated naming/collision/accessibility rules are locked;
- generator diagnostics have stable IDs and actionable messages;
- no known API rename/removal is deferred until after 1.0.

Any API that is still uncomfortable to support for years should change before the final release.

## Long-term compatibility requirements

The package must not encode assumptions that unnecessarily bind it to the exact release environment of 1.0.

Required gates include:

- future compatible modern TFMs select the modern runtime/generator path;
- lower compatible TFMs select the compatibility path;
- generator assemblies remain compiler-host compatible;
- a packed package is tested rather than relying only on project references;
- modern assets remain trimming/Native-AOT clean;
- Windows, Linux, and macOS validation remain green;
- Unity uses a clearly documented supported-editor baseline and receives real Editor/IL2CPP acceptance before release.

## Reliability requirements

The 1.0 line must have regression coverage for the failure modes users cannot easily diagnose themselves:

- event raised during subscription/setup;
- cancellation racing an event;
- timeout racing an event;
- disposal racing publication;
- source completion racing a lifecycle stop;
- stop-before-start lifecycle behavior;
- reconnect/repeat cycles;
- concurrent event producers;
- bounded-buffer drops;
- subscriber exceptions;
- cleanup exceptions;
- source generators over inheritance, generics, custom delegates, third-party targets, and name collisions.

Stress tests should concentrate on race boundaries rather than simply repeating happy paths.

## Package-quality requirements

A 1.0 package must be consumable without repository knowledge.

The shipped NuGet package must provide:

- one package ID for supported .NET TFMs;
- correct runtime and generator selection;
- XML documentation;
- README and icon;
- repository/source metadata;
- symbol/source support appropriate to all shipped runtime assets;
- deterministic package contents;
- no accidental development-only files;
- isolated consumer build and runtime smoke tests.

The Unity package must contain its own package metadata, documentation, samples, analyzer/runtime assets, and Unity asset metadata.

## Documentation requirements

The README should answer, in this order:

1. What problem does this solve?
2. What does the code look like before and after?
3. How do I install it?
4. What are the three or four most common usage patterns?
5. How do cancellation, buffering, and disposal behave?
6. Can I use it with third-party event sources?
7. Which frameworks/Unity versions are supported?
8. Where are the deeper lifecycle and performance contracts documented?

At least one realistic sample should demonstrate each major adoption path:

- legacy/third-party .NET events to `await`;
- event stream consumption;
- reconnecting/state-driven lifecycle;
- async implementation exposed to event-first consumers;
- Unity-native usage.

## Adoption-readiness requirements

Download count is an outcome, not a release gate. The 1.0 repository should nevertheless remove avoidable barriers to adoption.

Before release:

- the default branch represents the current stable product;
- GitHub release notes and a version tag exist;
- NuGet metadata is complete and searchable;
- package examples compile as written;
- the support matrix is obvious;
- migration from pre-1.0 versions is documented;
- the public API is small enough to understand without reading implementation docs;
- common misuse is prevented by API design or surfaced by diagnostics where practical.

## Performance requirements

AsyncEventBridge does not need to beat hand-specialized code in every benchmark. It must avoid pathological overhead for the convenience it provides.

Before 1.0:

- retain benchmark baselines for one-shot waits, streams, and bridges;
- investigate material allocation or throughput regressions;
- keep metrics/diagnostics opt-in or sufficiently cheap when unused;
- document any intentionally allocation-heavy paths where correctness/lifecycle ownership is the reason.

Performance changes do not justify compromising deterministic cleanup or race safety.

## Release policy

1.0 final is cut only after the public surface has completed a stabilization period with no known required breaking changes.

After 1.0:

- patch releases fix defects without expanding the conceptual model;
- minor releases may add additive interop capabilities;
- breaking changes wait for a major version and require a concrete benefit that outweighs ecosystem cost.

The default answer to a new feature request after 1.0 should be: can this be composed safely from the existing primitives? If yes, prefer documentation or an example over a new public API.
