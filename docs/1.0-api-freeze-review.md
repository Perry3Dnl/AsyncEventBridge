# 1.0 public API freeze review

This document records the pre-1.0 review of the AsyncEventBridge public contract.

The purpose is not to redesign working APIs for aesthetic reasons. A pre-1.0 breaking change is justified only when the current shape would create a long-term semantic trap, contradict normal .NET expectations, or leave an important compatibility contract unprotected.

## Changes accepted before the freeze

### Boolean EventCondition completion

The boolean convenience overload is:

```csharp
Task EventCondition.WaitUntilAsync(
    Func<bool> condition,
    Func<CancellationToken, Task> waitForChange,
    CancellationToken cancellationToken = default);
```

It deliberately returns `Task`, not `Task<bool>`.

Successful completion already means the condition became true. Returning a boolean added no state and implied that `false` might be a successful result. Callers that need the matching state snapshot use the generic `WaitUntilAsync<TState>` overload.

### Default lifecycle marker state

`EventStreamLifecycleEventKind` reserves zero:

```text
Unspecified     = 0
Activated       = 1
Value           = 2
Deactivated     = 3
SourceCompleted = 4
```

A default-initialized `EventStreamLifecycleEvent<T>` therefore cannot look like a real activation with an impossible cycle number.

### Bounded incoming-drop naming

The bounded mode that rejects the incoming event at capacity is named:

```text
EventStreamFullMode.DropWrite
```

not `DropNewest`.

The implementation maps to `System.Threading.Channels.BoundedChannelFullMode.DropWrite`. Channels already uses the name `DropNewest` for a different behavior: removing the newest item already buffered to accept the new write. Matching the BCL avoids permanent ambiguity and leaves the distinct `DropNewest` policy available as a future additive option if a real use case appears.

The associated metric tag is `drop_write`.

### Future-compatible generator selection

The unified package chooses the modern generator using target-framework compatibility with `net10.0`, rather than an exact target-framework equality check.

This prevents a future compatible TFM from selecting the modern runtime asset while accidentally receiving the compatibility generator.

## Public surface accepted for 1.0

Subject to the remaining validation gates, the following concepts are considered appropriate long-term public surface.

### Event to async

- `EventAwaiter`
- generated `<EventName>Async(...)`
- `EventStream`
- generated `<EventName>Stream(...)`
- `EventOccurrence<TSender, TPayload>` and modern sender-aware wait/stream APIs
- `EventCondition`
- `EventComposition`
- focused event-stream lifecycle composition through `EventStreamComposition`

These APIs all solve subscription lifetime, cancellation, race, buffering, or cleanup problems specific to event/async interop.

### Async to events

- `ToEventBridge()`
- `EventBridge`
- `EventBridge<T>`
- `EventStreamBridge<T>`
- bridge event args
- `EventBridgeOptions` and subscriber-exception policy

Explicit `Connect()` remains intentional. It gives callers a safe opportunity to subscribe terminal handlers before an already-completed task or synchronously advancing async sequence can publish.

### Source generation

The 1.0 generator model is:

- direct generation for supported classes and interfaces the caller owns;
- assembly-level generation for supported public third-party classes and interfaces;
- standard event-handler shapes and compatible custom two-parameter `void` delegates;
- diagnostics for unsupported shapes.

Interface targets are included before the 1.0 freeze because interface-typed event APIs are a normal .NET adoption path; `INotifyPropertyChanged` is the representative ecosystem case. Requiring callers to abandon an interface abstraction merely to use the generated façade would be a material interoperability gap.

For 1.0, interface discovery is intentionally conservative: generation covers events declared directly on the targeted interface. A base interface can be targeted independently. This avoids inventing ambiguous precedence rules for unrelated inherited interfaces that declare the same event name.

Struct targets remain rejected because extension-based subscription against copied value types would create surprising lifetime semantics.

## Configuration contracts accepted for 1.0

### EventStreamOptions

The mutable options object is retained.

Configuration is snapshotted when `EventStream.Create(...)` creates the stream:

- `Capacity`;
- `FullMode`;
- `DropObserver` on modern .NET.

`DroppedCount` is intentionally different: it is runtime telemetry owned by the options instance and aggregates drops across streams/enumerations that reuse that instance.

This mixed configuration/telemetry role is unusual but deliberate and already gives the options object a useful identity for drop accounting. The behavior must remain clearly documented.

### EventBridgeOptions

Bridge options are snapshotted when `ToEventBridge(..., options)` creates the bridge. Later mutation of the options instance does not reconfigure an existing bridge.

### Unbounded default

`EventStreamFullMode.Unbounded = 0` remains the default.

The alternative would be silent data loss. Memory-bounded behavior is therefore explicit through a bounded drop mode. AsyncEventBridge does not add a producer-blocking mode because blocking synchronous event callbacks changes event semantics and can deadlock.

## Result types accepted for 1.0

The dedicated composition result types remain preferable to expanding the API around tuples or a general union abstraction:

- `EventWaitAllResult<TFirst, TSecond>`
- `EventWaitAnyResult<TFirst, TSecond>`
- `EventWaitAnyResult<T>`

They keep the event-composition contract explicit without introducing a package-wide discriminated-union abstraction.

Default-initialized result structs are not library-produced successful results. No additional validity API is added for 1.0 unless a real consumption scenario requires it.

## Compatibility locks required before freeze closure

The API lock must protect more than exported type names.

Modern and compatibility test lines are expected to lock, as applicable:

- exported public types;
- exact public method names, return types, generic arity, parameter order/types, and optionality;
- public constructors;
- event handler types;
- property types and accessors;
- enum member names and numeric values;
- configuration defaults.

Generated API tests separately lock generated naming, overloads, generic constraints, accessibility, inheritance, and collision behavior.

## Explicit non-goals for the 1.0 public surface

The following remain outside the 1.0 contract:

- general async-LINQ operators;
- an `IObservable<T>` / Rx replacement;
- scheduler abstractions;
- dependency-injection or logging-framework integrations;
- transport-specific bridges;
- retry/backoff policy;
- persistence or replay;
- a blocking event-stream backpressure mode.

These can be built above the existing primitives or evaluated later from actual adoption evidence.

## Remaining freeze review

Before declaring the public surface frozen, complete:

- nullability review of all exported members and generated APIs;
- XML documentation completeness;
- generator diagnostics/message review;
- modern versus .NET Standard API-difference documentation;
- Unity-specific public-surface review;
- packed-package compile/runtime validation using the candidate API;
- migration notes for all pre-1.0 source-breaking changes.

Once those checks are complete, public API changes should require the same level of justification expected after a stable 1.0 release.
