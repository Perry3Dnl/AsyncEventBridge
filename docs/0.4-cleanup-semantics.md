# 0.4 cleanup exception semantics

AsyncEventBridge 0.4 defines one ordering rule for failures that occur while an event operation is terminating:

> The primary operation outcome is preserved first. Cleanup failures are appended after it instead of replacing it.

This applies to one-shot waits, event streams, sender-aware occurrence APIs through their shared engines, and async-stream bridge enumerator cleanup.

## Contract

| Primary outcome | Cleanup outcome | Observable result |
| --- | --- | --- |
| Success | Success | Original success |
| Success | One cleanup failure | Cleanup exception |
| Success | Multiple cleanup failures | `AggregateException` containing cleanup failures in cleanup order |
| Fault | Success | Original fault |
| Fault | Cleanup failure(s) | `AggregateException`: primary fault first, cleanup failure(s) after it |
| Cancellation | Success | Cancellation |
| Cancellation | Cleanup failure(s) | `AggregateException`: `OperationCanceledException` first, cleanup failure(s) after it |
| Timeout | Success | `TimeoutException` |
| Timeout | Cleanup failure(s) | `AggregateException`: timeout first, cleanup failure(s) after it |

When cleanup itself fails, the overall operation is considered faulted. A cancellation plus a cleanup failure is therefore faulted with an aggregate rather than reported as a clean cancellation.

## EventAwaiter

`EventAwaiter` already owned explicit cleanup of event unsubscription, cancellation registrations, and timeout registrations. In 0.4 those failures use the common ordering contract for every terminal state, including cancellation and timeout.

The simple wait fast path follows the same rule.

## EventStream

Event streams no longer rely on a throwing `finally` block that can replace an exception already being propagated by the stream. Stream reads capture their terminal exception, cleanup runs, and the two outcomes are combined deliberately.

This also means early `DisposeAsync()` of an event-stream enumerator surfaces an unsubscribe failure directly.

`EventOccurrenceStream` inherits these semantics because it delegates subscription lifetime to `EventStream`.

## EventStreamBridge

The stream bridge now drives the source `IAsyncEnumerator<T>` explicitly so a `MoveNextAsync` failure and an enumerator `DisposeAsync` failure can both be retained.

If source enumeration fails and enumerator cleanup also fails, the `Faulted` event receives an `AggregateException` with the source failure first.

If owner `DisposeAsync()` causes cancellation and enumerator cleanup then fails, the returned `ValueTask` faults with an aggregate containing cancellation first and cleanup second. Owner disposal still suppresses terminal bridge events.

Synchronous `Dispose()` cannot await asynchronous enumerator cleanup. If asynchronous cleanup later fails after synchronous owner disposal, the failure is written to `Trace`.

## EventBridge

`EventBridge` for `Task`/`ValueTask` has no external unsubscribe or async-enumerator resource to release. Disposal only clears owned handler references, so there is no fallible cleanup callback to combine. Subscriber-exception policy remains a separate 0.4 design topic.

## EventComposition

Composition intentionally cancels losing waits. If a losing wait reports an aggregate containing that expected cancellation plus a cleanup failure, composition removes the expected loser cancellation and continues to surface the actual cleanup failure. This preserves the existing `WaitAny`/`WaitAll` cleanup contract while still retaining cancellation when callers use `EventAwaiter` directly.

## Compatibility

The same behavior is implemented in:

- modern .NET runtime;
- .NET Standard 2.0 compatibility runtime;
- Unity portable core.

The compatibility and Unity copies remain byte-for-byte aligned where required by the convergence CI.
